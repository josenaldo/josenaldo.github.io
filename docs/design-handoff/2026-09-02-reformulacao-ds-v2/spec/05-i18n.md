# 05 — Chaves de i18n e de conteúdo

Tudo que os componentes de `code/` esperam e que **não existe hoje**. Sem isto,
`next-intl` lança `MISSING_MESSAGE` em desenvolvimento e renderiza a chave em
produção — então esta é a primeira coisa a fazer, antes de trocar qualquer
componente.

Convenção do projeto mantida: `messages/en.json` e `messages/pt.json`, mesma
árvore, mesma ordem de chaves.

## 3. Home.workModes — título novo + kicker no frontmatter

```json
"workModes": { "title": "Three ways to work with me" }
```
```json
"workModes": { "title": "Três formas de trabalhar comigo" }
```

O kicker de cada modalidade é **conteúdo**, não tradução: entra como campo novo
no frontmatter de `content/workModes/*.md` e no schema de
`contentlayer.config.js` (`kicker: { type: 'string', required: false }`).

| Arquivo | `kicker` (EN) | `kicker` (PT) |
|---|---|---|
| rescue | `Fixed scope · fixed duration` | `Escopo fixo · duração fixa` |
| delivery-machine | `Monthly retainer` | `Retainer mensal` |
| build | `End to end` | `Ponta a ponta` |

Sem o campo, a pílula não renderiza e o card segue válido — mas o card perde a
informação comercial mais importante (como se contrata).

## 5. Metrics.<id>.resultCaption — legenda do número no bloco Result

O `label` da métrica é curto para caber no card do hero ("Release cadence"). No
bloco Result ele fica ambíguo — o número precisa dizer de onde para onde. Chave
nova, opcional: sem ela o componente cai no `label`.

| id | `resultCaption` (EN) | `resultCaption` (PT) |
|---|---|---|
| `deploymentFrequency` | approved request to production (was 3–6 months) | do pedido aprovado à produção (era 3–6 meses) |
| `clientReportedIssues` | client-reported issues a month (was ~100) | chamados do cliente por mês (eram ~100) |
| `deployDuration` | push to production (was 2h) | do push à produção (eram 2h) |
| `followUpOperation` | monthly follow-up operation (was a month of manual work) | operação de acompanhamento mensal (era um mês de trabalho manual) |
| `muvzDelay` | months of delay left | meses de atraso restantes |
| `muvzPerformance` | system performance | desempenho do sistema |
| `muvzSprintCadence` | sprint cadence held after I rolled off | cadência de sprint mantida após minha saída |
| `conddizArchitecture` | frontends on one backend | frontends sobre um backend |
| `conddizTrafficPeak` | users at peak traffic | usuários no pico de tráfego |

## 9. Ordem de execução

1. Adicionar **todas** as chaves acima nos dois arquivos de mensagem.
2. Adicionar `kicker` ao schema do Contentlayer e aos três `workModes/*.md`.
3. Rodar `yarn build` — o build deve passar **antes** de qualquer troca de
   componente. Se falhar aqui, falha por conteúdo, não por layout.
4. Só então seguir a ordem de `spec/04-aceite.md §1`.
